# MCU 接入说明（待板端验证）

## 接口与资源

将 `c/src/serial_frame.c` 纳入编译，增加 `c/include` 头文件路径，使用 C99。
无 `malloc/free`、HAL、RTOS、系统时钟或串口依赖，时钟由调用方提供。
用 `sizeof(sf_parser)` 获取目标平台实际状态内存；其中帧缓冲区固定 260 字节。
编码另外需要调用方提供至多 260 字节的输出缓冲区。

CRC 逐位计算，每个字节处理 8 个 bit；未做查表优化。
核心每次最多积累一帧，不因 feed 数据块增大而扩容。
具体栈使用量、周期数、吞吐率仍需目标平台编译和测量。

## 裸机接收循环

建议的数据路径：

```text
UART RX 中断 / DMA 完成事件
    → 驱动管理的接收缓冲区
    → 主循环取出稳定数据块
    → sf_feed(..., board_millis(), ...)
    → on_frame 内处理或复制 payload

主循环无新数据时 → sf_tick(..., board_millis())
```

核心不包含 UART 驱动或环形队列。接收缓冲区的生产消费、溢出处理和并发安全由适配层负责。
不要直接假设 `volatile` 能替代同步。

ISR 尽量只提交数据或更新接收位置；不要在中断里执行阻塞日志、复杂协议处理。
如果采用 DMA 环形缓冲，需要处理绕回、消费者落后、DMA 数据可见性以及目标芯片的缓存维护。
在调用 `sf_feed()` 期间，传入数据必须保持稳定，不能被 DMA 覆盖。
这些工作应根据具体 MCU、驱动和存储器布局实现，当前没有提供可直接烧录的 HAL 工程。

## RTOS 使用

让同一个接收任务独占一个 `sf_parser`，以有限等待接收队列数据。
读到数据时调用 `sf_feed()`，超时返回后调用 `sf_tick()`。
不要从定时器任务和接收任务同时调用同一个解析器。
如果回调需要通知业务任务，复制 payload 到有明确所有权的队列项或内存池，
不可把解析器内部指针直接排队。

计数器是 `uint32_t`，累计溢出按无符号规则回绕；需要长期统计时在上层做差量汇总。

## 超时怎么设置

这里实现的是**整帧组装期限**，从候选首字节开始，后续新字节不会续期，
不是 UART IDLE 检测，也不是每两个字节之间的空闲超时。

8N1 下每字节需要约 10 个串行 bit。以 115200 baud 为例，
260 字节满长帧的纯线上传输时间约为 `260 × 10 / 115200 ≈ 22.6 ms`。
超时还需覆盖发送端暂停、收数调度和本地任务延迟；README 的 100 ms 仅为演示值。
低波特率下应重新计算，例如 9600 baud 满长帧约需 271 ms。

`now_ms` 要使用单调递增的 `uint32_t` 毫秒 tick，而非日历时间。
实现通过无符号差值支持回绕；启用超时范围为 1–INT32_MAX ms。
调度应保证至少每 `2^31` ms 调一次，并尽量远短于配置超时。
`sf_init(..., 0)` 禁用超时；注意这与 Python 的 `None` 表示不同。

## 故障恢复取舍

`AA 55` 可能出现在合法 payload 内，因此当前策略在 CRC 失败后丢弃整个候选帧，
不对候选内部进行重新扫描。这样实现简单、行为明确，但长度被改大时可能吞掉后续帧。
使用半帧超时可终止等待，无法保证任意错误下下一帧一定保留。
如果业务要求更强恢复或可靠交付，可另行设计转义/COBS、序列号、ACK 与重传；
这些都涉及线协议变化，应与现有协议兼容性一起考虑。
