# 项目经历与面试准备

## 当前可用的项目定位

**UART 帧编解码与异常恢复组件｜C99、Python、单元测试、GitHub Actions**

完成代码理解并复现测试后，可以按自己实际参与和理解程度改写：

- 基于固定帧头、长度字段和 CRC-16/MODBUS 实现 C99 流式编解码，
  使用固定 260 字节帧缓冲区、无动态内存，支持拆包、连续多帧与错误统计。
- 实现由外部单调时钟驱动的半帧超时，覆盖滴流不续期、超时边界及 32 位时钟回绕；
  保留 Python 参考实现，并通过全 payload 长度和拆包边界测试及跨语言互操作验证协议一致性。

CI 配置、文档和测试可以作为工程能力补充，通常不必各占一条简历。
不要写“STM32 DMA 收发”“FreeRTOS 集成”“工业级可靠性”或任何吞吐率数据，
除非你已经实现、测试并能展示证据。协助生成的代码也应逐段理解、验证再用于面试。

## 容易被追问的内容

1. **UART 的一次 read 为什么不等于一帧？**
   说明传输字节流、驱动缓冲和业务帧边界的区别，再用半帧与连续多帧举例。
2. **CRC 覆盖了哪些字段？大小端怎么约定？**
   解释长度参与 CRC、CRC 小端放置，以及标准向量为什么有用。
3. **为什么要 tick？为什么不每来一个字节就更新时间？**
   对端断线时没有新事件；当前期限限制整帧组装时间，滴流不能无限续命。
4. **计时器回绕怎么算？**
   写出 `(uint32_t)(now - start)`，结合约定的调度间隔解释其适用范围。
5. **LEN 被干扰后能恢复吗？**
   如实说明可能等待超时或吞掉后续帧；比较整候选丢弃与内部扫描的取舍。
6. **为什么不在回调里把 payload 指针直接传给另一个任务？**
   指针指向可复用内部缓冲区；异步消费前应复制或建立独立所有权。
7. **测试为什么不只用 build 再 parse？**
   同源编解码可能共享错误；标准 CRC 向量、跨语言对比和边界/故障输入提供补充证据。
8. **下一步怎样接开发板？**
   画出 UART → 驱动缓冲 → 接收任务 → 解析器 → 业务队列，说明溢出和并发的责任边界。

## 下一阶段最有价值的补充

选择一块现有开发板，完成 UART 适配和故障注入，并保存可复现日志。
之后再根据实际工作补充中断/DMA/RTOS、资源开销和性能测量。
本项目适合作为嵌入式项目中的通信组件；能否体现完整系统能力，取决于后续板端应用。
